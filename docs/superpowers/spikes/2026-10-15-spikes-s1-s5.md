# Rapport des spikes S1 à S5

- Date : 2026-10-15
- Versions testées : Claude Code 2.1.301, tmux 3.5a (WSL2, Linux 6.18)
- Référence : spécification `docs/superpowers/specs/2026-10-15-meute-design.md`, § 14
- Méthode : un dépôt jetable sans remote, des hooks et une statusline de capture passés par `--settings`, un serveur tmux isolé (`-L meute-spike`). Aucun code n'est conservé.

## Synthèse

| Spike | Résultat | Impact sur la spécification |
|---|---|---|
| S1 — options de `claude` | ✅ toutes présentes. `--session-id` est respecté en mode interactif mais **ignoré avec `--bg`** | Mineur |
| S2 — hooks | ✅ états observables : en cours, permission demandée, tour terminé, fin | Mineur : filtrer le bruit (§ S2) |
| S3 — statusline | ✅ `session_id`, quotas **avec l'heure de reset**, dépôt distant, worktree | Positif : la détection de la forge est gratuite |
| S4 — tmux | ✅ échange entre sessions, imbrication, raccourcis `M-*` | Mineur : options **de pane**, pas de fenêtre |
| S5 — worktrees natifs | ✅ `claude -w <nom>` dans `<dépôt>/.claude/worktrees/<nom>` | À trancher : convention native ou celle du § 11 |
| Hors spikes | ⚠️ **Claude Code gère nativement des sessions en arrière-plan** (`--bg`, `claude agents`) | **Structurant**, à discuter |

## S1 — Options de `claude`

| Option | Résultat |
|---|---|
| `--settings <fichier>` | ✅ Les hooks et la statusline du fichier sont exécutés |
| `--mcp-config`, `--append-system-prompt` | ✅ présentes. Le contenu effectif reste à vérifier pendant l'implémentation |
| `--session-id <uuid>` | ✅ respecté en mode interactif (`SessionStart.session_id` = l'UUID demandé). ❌ **ignoré avec `--bg`**, qui attribue son propre identifiant |
| `-n, --name <nom>` | ✅ renvoyé dans `session_title` / `session_name` |
| `--permission-mode <mode>` | ✅ valeurs : `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan` |
| Variable d'environnement `MEUTE_SESSION` | ✅ transmise à chaque hook et à la statusline |

**Confiance dans le dossier.** Un dossier jamais ouvert affiche la question de confiance. La réponse par défaut est « No, exit ». En mode `--bg`, la session refuse de démarrer (« Workspace not trusted »). La confiance s'applique à un dossier précis et **ne s'hérite pas** du dossier parent. Elle est stockée dans `~/.claude.json` (`projects[<chemin>].hasTrustDialogAccepted`).
→ En mode interactif dans tmux, l'utilisateur répond lui-même à la question dans la zone principale. meute ne doit pas modifier `~/.claude.json`.

**Incident instructif.** Une session `--bg` lancée sans `--permission-mode` a hérité du mode `auto` de l'utilisateur. Elle a créé un worktree, commité, puis poussé une branche sur le dépôt public.
→ **Règle à ajouter à la spécification** : meute passe toujours un `--permission-mode` explicite (par défaut, celui de la configuration de meute, `manual` si rien n'est défini) et l'affiche dans la liste des sessions.

## S2 — Hooks

Contenu commun à tous les messages : `session_id`, `transcript_path`, `cwd`, `hook_event_name`, et la plupart du temps `prompt_id` et `permission_mode`.

| Hook | Champs utiles | État dans meute |
|---|---|---|
| `SessionStart` | `source` (`startup`…), `model`, `session_title` | `Idle` + `native_id` |
| `UserPromptSubmit` | `prompt`, `permission_mode` | `Running` |
| `PreToolUse` / `PostToolUse` | `tool_name`, `tool_input` | `Running`, dernier outil appelé |
| `PermissionRequest` | `tool_name`, `tool_input`, `permission_suggestions` | `PermissionRequested` (avec le détail de la demande) |
| `Notification` | `notification_type: "permission_prompt"`, `message` | redondant avec `PermissionRequest` |
| `Stop` | `last_assistant_message` | `Idle` + aperçu du résultat |
| `SubagentStop` | `agent_type` | voir le bruit ci-dessous |
| `SessionEnd` | — | `Exited` |

Constats :

- `PermissionRequest` est plus précis que `Notification` : il indique l'outil et l'argument concernés. meute s'appuie sur lui.
- **Bruit** : un `SubagentStop` avec `agent_type: ""` est émis pour des tâches internes (par exemple la suggestion de prompt « commit this »). meute doit ignorer les `SubagentStop` dont `agent_type` est vide.
- Aucune `Notification` de type inactivité (`idle_prompt`) n'a été observée après plusieurs minutes d'attente. L'état « attend ta réponse » se déduit donc de `Stop`, et non d'une notification.
- `Stop.last_assistant_message` permet d'afficher la dernière réponse dans le panneau de détails, sans lire le transcript.

## S3 — JSON de la statusline

Champs utiles relevés (version 2.1.301) :

```
session_id, session_name, version, transcript_path
model.id, model.display_name, effort.level, fast_mode, thinking.enabled
workspace.current_dir, workspace.project_dir, workspace.git_worktree
workspace.repo.{host, owner, name}                ← détection de la forge
cost.{total_cost_usd, total_duration_ms, total_api_duration_ms,
      total_lines_added, total_lines_removed}
context_window.{used_percentage, remaining_percentage, context_window_size,
                total_input_tokens, total_output_tokens, current_usage.*}
rate_limits.five_hour.{used_percentage, resets_at}  ← horodatage epoch en secondes
rate_limits.seven_day.{used_percentage, resets_at}
worktree.{name, path, branch, original_cwd, original_branch}
prompt_cache.{warm, ttl, expires_at, hit_ratio, ...}
```

- La statusline est aussi appelée **en mode `--bg`** : 20 appels pour une session de 20 secondes. Les métriques sont donc disponibles même sans terminal attaché.
- La fréquence est élevée. La limitation d'écriture prévue au § 7.2 (n'écrire qu'en cas de changement, ou au plus une fois toutes les 30 s) est nécessaire.
- `prompt_cache.expires_at` ouvre une idée pour plus tard : signaler qu'une session inactive va perdre son cache.

## S4 — Disposition tmux

Testé sur un serveur isolé avec une session `meute` (zone principale et tableau de bord de 60 colonnes) et une session `bg` (une fenêtre par session gérée).

| Point | Résultat |
|---|---|
| `swap-pane` entre deux sessions tmux | ✅ Le panneau change de taille (de 200 à 139 colonnes) et Claude se redessine |
| Survie du processus après plusieurs échanges | ✅ Claude reste réactif (« pong ») |
| Option `@meute_id` | ⚠️ **Une option de fenêtre reste attachée à la fenêtre** et ne suit pas le panneau. De plus, une option de pane hérite de celle de la fenêtre. → N'utiliser que des options **de pane** (`set -p`) |
| `remain-on-exit` | ⚠️ Même problème : il faut l'utiliser comme option **de pane**. On obtient alors `pane_dead=1` et `pane_dead_status=3` ✅ |
| Fermeture du panneau principal | ⚠️ Le tableau de bord occupe alors toute la largeur. meute doit recréer un panneau de remplacement |
| Imbrication dans un autre tmux (`env -u TMUX tmux -L … attach`) | ✅ fonctionne |
| Raccourcis `bind -n M-p` / `M-o` à travers le tmux externe | ✅ transmis, le focus change bien (le tmux externe testé n'avait pas de raccourci `M-p`) |
| `status-right` alimenté par une option `@meute_status` | ✅ |

Point restant : sous un tmux externe qui utilise lui-même `M-p` ou `M-o`, ces raccourcis seront interceptés. Ils doivent donc être configurables, comme le prévoit déjà la spécification.

## S5 — Worktrees natifs

- `claude -w/--worktree [nom]` et l'outil `EnterWorktree` créent `<dépôt>/.claude/worktrees/<nom>` sur une branche `worktree-<nom>`.
- `claude rm <id>` supprime le worktree « quand c'est sûr ».
- `claude --tmux` (avec `--worktree`) crée lui-même une session tmux.
- Une session `--bg` peut décider seule de créer un worktree (observé).
- Le dossier `.claude/worktrees/` se trouve **dans** le dépôt. S'il n'est pas ignoré, il apparaît dans `git status` du dépôt principal.

## Découverte hors spikes : les sessions natives en arrière-plan

Claude Code 2.1.301 fournit :

- `claude --bg` : lance une session sans terminal et affiche un identifiant court ;
- `claude attach <id>` : ouvre la session dans le terminal courant ; `←` revient à la vue des agents, `Ctrl+Z` au shell ;
- `claude logs`, `stop`, `respawn` et `rm` ;
- `claude agents` : une vue interactive des agents ;
- `claude agents --json` : liste **toutes** les sessions actives, interactives comprises, avec `pid`, `cwd`, `kind`, `sessionId`, `name`, `status` (`busy` / `waiting` / `idle`) et `state`.

`claude agents --json` est une source d'état **officielle et gratuite**, qui couvre aussi les sessions lancées en dehors de meute. Elle complète les hooks, qui restent plus riches : outil appelé, détail de la permission, dernière réponse.

Questions ouvertes pour la suite :

1. Faut-il que meute lance Claude directement dans un panneau tmux (spécification actuelle), ou lance `claude --bg` puis affiche `claude attach <id>` dans la zone principale ?
2. Faut-il utiliser `claude agents --json` pour découvrir les sessions lancées hors de meute ?
3. Faut-il adopter la convention native des worktrees ou garder celle du § 11 ?

## Modifications proposées pour la spécification

1. § 6.2 : `--permission-mode` toujours explicite et affiché. Valeur par défaut configurable, `manual` par défaut.
2. § 5.1 et § 5.4 : `@meute_id` et `remain-on-exit` utilisés comme options de pane. Recréation du panneau principal s'il disparaît.
3. § 7.1 : s'appuyer sur `PermissionRequest`, ignorer les `SubagentStop` dont `agent_type` est vide, état « attend » déduit de `Stop`, afficher `last_assistant_message`.
4. § 7.2 : liste des champs confirmés. Heure de reset disponible. `workspace.repo` utilisé pour la forge en V1.1.
5. § 6.2 : prévoir le cas « dossier non approuvé » (la question s'affiche dans la zone principale).
6. Sessions natives en arrière-plan, worktrees natifs : décisions à prendre (voir les questions ci-dessus).
